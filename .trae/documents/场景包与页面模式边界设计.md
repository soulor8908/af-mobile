# 场景包与页面模式边界设计

> 日期：2026-08-26
> 背景：E2E 验证后头脑风暴确认的三个质疑——(1) 场景包的品类视角与 Few-shot 页面模式视角边界不清；(2) "高频场景"缺数据来源；(3) 目标客户画像未锚定。
> 客户画像决策（用户确认）：**C 端消费类为主**——审美基线（对标小红书/美团/Apple H5）维持，场景包优先级以此为序。

## 1. 问题：两层职责混淆

规划中的 7 品类 19 场景包（电商 cart/order/coupon、O2O booking/store-map/review…）是"App 品类"分类法。但 AI 实际逐页生成时遇到的是**页面模式**：

- 电商 App 也有登录表单（page-form）、列表页（page-list）
- 工具 App 也有商品卡（page-detail 的 card-media）

若场景包重复提供页面模式指导，会与 Few-shot 层冲突（两个真相源），且 19 个包 × 每包重复页面模式 = prompt 膨胀。

## 2. 双层模型（边界定义）

| 层 | 职责 | 内容形态 | 数量 |
|---|---|---|---|
| **Few-shot 层** | 页面模式（跨品类原子能力） | page-list / page-detail / page-form / page-login / page-search / page-profile / page-empty / app-shell 示例 | 8 个固定示例，按需检索 |
| **场景包层** | 品类骨架（品类专属布局与组件组合约定） | 如 O2O 的"门店卡 + 定位条 + 购物栏"、电商的"SKU 规格区 + 优惠信息条" | 按需落地，关键词注入 |

**判定规则**：某条指导如果对所有品类都成立（"列表要有卡片化列表 + 彩色状态标签"），归 Few-shot/通用规范；只有切换品类才成立（"点单页必须有门店信息条"），归场景包。

## 3. C 端优先级（数据驱动前的默认序）

```
marketing（已落地）→ ecommerce → o2o → content → social → education / tool / enterprise
```

- enterprise 降到最后：工具型页面朴素是合理的（P0-3 改进方案已确认），不注入高视觉基准
- 优先级是**默认序**，真实序由遥测数据修正（见 §4）

## 4. 数据驱动落地（补数据环，已实现）

### 4.1 需求分布遥测

- `build-prompt.mjs`：全部 8 个品类包（含未落地）参与 `detectSceneDemand()` 关键词探测，多标签
- `telemetry.mjs`：`recordRun` 新增 `kind`（lint/prompt）与 `scene`（命中的场景包 key 数组）字段；**只记封闭集的 key，不落需求原文**（隐私红线不变）
- `get_prompt`（MCP）与 `generate.mjs`（CLI）在构建 prompt 时记录 `kind='prompt'` 事件
- `flywheel.mjs`：分析层新增"场景需求分布"段（按命中计数降序 + 来源分布）；prompt 事件不掺水规则榜/收敛度

### 4.2 落地决策流程

```
npm run eval:flywheel → 看"场景需求分布" Top 品类
→ Top 品类 ≠ 默认序头部时，优先落地 Top 品类的场景包
→ 落地动作：SCENARIO_PACKS 该包补 body（品类骨架，按 §2 判定规则写）+ implemented: true
→ npm run prompt + prompt:check（快照同步）
```

未落地包从第一天起就记需求数据——**先有分布，再谈落地，不拍脑袋**。

## 5. 误命中防护（已实现）

营销/首页场景包注入高视觉基准的前提是"消费场景"。企业后台/管理端的"首页"不是营销场景：

- `negativeKeywords: ['后台', '管理端', 'dashboard', '仪表盘', '审批', '工单', '内部系统', 'admin', 'erp', 'OA']`
- 命中任一负向词 → 不注入营销包（需求分布同样不计 marketing，记 enterprise）
- 未来每个高视觉场景包落地时须同步评估自己的负向词表

## 6. 新场景包落地 checklist

- [ ] 遥测分布确认该品类为 Top 需求（或按默认序推进）
- [ ] body 只写品类骨架，逐条过 §2 判定规则（通用指导上移到 Few-shot/通用规范）
- [ ] keywords 封闭集 + 评估 negativeKeywords（防跨品类误命中）
- [ ] `implemented: true` + `npm run prompt` + `prompt:check` + `whitelist:check`
- [ ] test/build-prompt.test.js 补该包的正/负命中用例
- [ ] E2E：用该品类典型需求走一遍 generate → lint 闭环（参照 `.workbuddy/原型样式诊断/e2e/`）

## 7. 与验证体系的关系

本设计是"验证充分性"头脑风暴的产出之一，配套：

- **修复循环回归**（test/fix-loop-regression.test.js）：错误恢复表引导力 + RULE_HINTS 全覆盖闸门
- **E2E 原型矩阵**（e2e/prototype/）：3 页高视觉原型 + 空态/错误态夹具的渲染与导航回归
- **多模型验证**（未自动化）：不同 LLM 用同一裁剪 prompt 生成的合规率对比——需人工或配置 AFMOBILE_AI_API_URL 后跑 generate.mjs
