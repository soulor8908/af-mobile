# AI 写得出 demo，落地靠选型 —— AIFlow Starter 技术决策实录

> 2026-08 · 配套详细设计：[starter-landing-design.md](../design/starter-landing-design.md)

## 引子：屎山经济学

用 AI 写过移动端应用的人都知道那条曲线：第一天，demo 跑起来了，激动；第一周，开始修 bug，每个 bug 一轮对话；第一个月，token 账单超过预算，页面还是不能上线。

这不是模型不行，是**结构**不行：

```
AI 开发总成本 = 生成（1x） + 修复循环（5-10x） + 人工验收（∞）
                          ↑ 全部溢价在这一段
```

我们做 AIFlow UI 时反复问一个问题：这条链上，到底哪一段最容易被 AI 搞砸？答案出乎意料地整齐——

| 环节 | AI 翻车率 | 原因 |
|---|---|---|
| 后端 CRUD | 低 | schema 是天然约束，且 BaaS 已把它变成填表 |
| 部署 | 低 | 云平台连 Git 即上线 |
| 鉴权 | 低 | 调 SDK，AI 抄文档很稳 |
| **前端 UI** | **高** | **AI 看不见屏幕**：状态同步、无障碍、跨端一致性，没有 schema 可依，没有编译器兜底 |

后端和部署已经被生态标准化了。**前端是落地链上最后一段每次现场手搓的环节。** 这就是为什么我们的落地方案（AIFlow Starter）敢只做前端、却宣称解决"落地"——不是傲慢，是分工：翻车率最高的那段做成标准件，其余各段指向已被验证的标准答案。

下面是这份方案里的十个技术选型。每个都遵循同一个格式：**问题 → 备选 → 决策 → 我们会在什么情况下承认自己错了。**

---

## 选型 1：静态产物 + BaaS，而不是全栈框架

**问题**：用户要"落地"，为什么不直接用 Next.js 一把梭？

**备选**：Next.js / Nuxt 全栈 + 数据库 ORM + 自建 API 层。

**决策**：前端是纯静态产物（`dist/`），后端收敛到 Supabase（BaaS），中间零自建服务。

理由有三。其一，翻车率定价：全栈框架把翻车率最低的两段（后端、部署）重新变成代码，等于花钱买风险。其二，AI 在"胶水层"（API route、ORM 模型、数据转换）上产屎山的效率极高——每一段胶水都是一轮潜在的修复循环。其三，我们的核心资产是 28 个预验证 Web Components（988 个测试、23.8KB gzip），塞进任何框架的渲染管线都是削足适履。

**证伪条件**：如果真实用户中出现大量"必须自建后端逻辑"的场景（复杂事务、长任务、实时协作），静态 + BaaS 的边界就到了，届时再谈 Workers/边缘函数层。

---

## 选型 2：契约面收敛为一个函数签名，而不是协议动物园

**问题**：前端组件怎么消费后端，才不至于每换一个后端就重写一遍？

**备选**：tRPC（端到端类型）、OpenAPI codegen（schema 生成客户端）、GraphQL 客户端。

**决策**：全部否掉，收敛为一个最小契约：

```js
async function query(resource, { page, pageSize, signal }) {
  // return { data: T[], total: number }
  // throw FetchError 家族
}
```

`{ data, total }` 不是我们发明的协议——它是主库 `fetchPage` + `af-data` 已经在工作的事实协议（af-list 的 loadmore 判停依赖 `total`）。规范化已有事实，成本为零；引入 tRPC 意味着前端必须长出 Node 侧类型系统，OpenAPI codegen 意味着用户要先学会维护 schema——两者都违反"用户不想管事"的第一性约束。

**证伪条件**：若用户大量抱怨类型不安全（改后端字段前端不报错），再考虑在 adapter 层挂可选的 schema 校验，而不是把类型系统塞进核心。

---

## 选型 3：adapter 独立包 + peer 依赖，死守零依赖红线

**问题**：Supabase adapter 放哪里？

**备选**：塞进 `@af-mobile/ui` 主包（方便）；塞进 Starter 模板（复制即用）。

**决策**：独立包 `@af-mobile/adapters`，`peerDependencies: { "@supabase/supabase-js": "^2" }`。

主包的立身之本是**零运行时依赖 + 23.8KB gzip 体积**，塞进 supabase-js（数百 KB）等于自毁招牌；塞进模板则更糟——模板被复制后就是孤儿，adapter 的 bug 修无法回流。peer 依赖的代价是用户多装一个包，收益是"不用 BaaS 的人完全无感"。

**证伪条件**：无。这是一条红线，不是权衡。

---

## 选型 4：主包只加 30 行的 scheme 注册表

**问题**：`fetchPage` 怎么认识 `supabase://` 这种 URL？

**决策**：主包只提供分发机制，不带任何具体实现：

```js
registerBackend('supabase', supabaseAdapter);   // 注册
<af-data src="supabase://products?category=eq.shoes">  // 使用
```

`supabase://` 的翻译规则（PostgREST 语法、`Range` 头分页、`Prefer: count=exact` 解析 total）全部住在 adapter 包里。主包增加的只有约 30 行注册表代码（+38B gzip，coreRuntime 实测 5.04KB / 预算 5.4KB）。

这个切分的原则是：**分发机制是通用能力，具体 adapter 是生态选择。** 未来 `firebase://`、`d1://`、`r2://` 都挂同一个钩子，主包永远不用为此发版。

**证伪条件**：如果某 adapter 的语法复杂到 30 行注册表表达不了（如需要连接池、订阅流），就该升级为独立的 resource 协议讨论，而不是偷偷往主包塞逻辑。

---

## 选型 5：首个 BaaS 选 Supabase，安全模型必须先讲清楚

**问题**：Firebase、PocketBase、Supabase 选谁？

**决策**：Supabase。决定性因素不是功能表，是**安全模型能不能被模板安全地默认**：

1. anon key 进前端 bundle 是**官方设计**——安全性由 RLS（Row Level Security）承担，不由 key 保密承担。这对"用户不想管事"至关重要：我们能在 `schema.sql` 里默认开 RLS、预置三条最小策略，用户无感获得正确安全基线；
2. PostgREST 让"数据库即 API"，`supabase://` 的翻译层薄到纯 URL 拼接；
3. 开源可自托管，逃离路径存在（PocketBase 同构可接）。

**证伪条件**：如果实测 PostgREST 复杂查询（多表聚合、全文搜索）翻译层开始变厚，就到了"模板只覆盖简单 CRUD、复杂场景指路给官方 SDK"的边界——这边界要写进文档，而不是假装没有。

---

## 选型 6：Vite 只当打包器，不引入任何框架

**问题**：Starter 用什么脚手架？

**决策**：`vite.config.js` 接近空文件。没有 React/Vue/Svelte，没有 SSR 插件，没有路由插件——主库自带路由（History 模式 + keep-alive + View Transitions）、状态（signal/computed）、数据（fetchPage）。

Web Components + 原生能力（Popover API、scroll-snap、Declarative Shadow DOM）是 23.8KB 的来源；任何框架层都是在这个数字后面加零。AI 生成代码时，框架层还意味着第二套心智模型和第二份文档要读。

**证伪条件**：用户生态强烈要求 React/Vue 包装层时，做官方 wrapper 包（如同 web components 生态惯例），而不是把框架塞进核心。

---

## 选型 7：路由默认 History 模式，hash 做逃生舱

**问题**：History 模式要服务器配置（刷新即 404），hash 模式零配置但 URL 丑——默认哪个？

**决策**：默认 History（`/goods/123`，SEO 友好），`start('#app', { hash: true })` 一行切 hash。

这个选型的实现成本极低（净增约 15 行 + 38B gzip），但它背后是一次角色认知的修正：**部署配置是落地链的一部分，库引入的坑库要负责给出填坑说明。** 所以 README 部署速查表现在覆盖六个平台（nginx / Vercel / Netlify / Express / Caddy / Cloudflare Pages），每条都是三行以内。

demo 阶段点导航永远正常（不触发刷新），部署后一刷新就 404——这个哑巴坑 AI 永远不会主动告诉你，因为它看不见服务器。

**证伪条件**：无。两模式共存即终态。

---

## 选型 8：三页模板不是功能演示，是 few-shot

**问题**：Starter 里放什么页面？

**备选**：组件大杂烩 demo 页 / 空白骨架。

**决策**：三页——login（Auth + 路由守卫）、list（分页 + loadmore + 下拉刷新）、detail（`:param` 路由 + 资源缓存）。

逻辑是：AI 改造参照实现，比读懂文档快一个数量级。这三页覆盖移动端 CRUD 应用的约 80% 骨架，且每一页都是"契约路径的验证过的参照"——用户/AI 抄的是**已被测试背书的结构**，不是搜索结果第一页的十年前写法。

**证伪条件**：benchmark 中若发现 AI 在三页之外的页面类型（表单流、多步向导）首过率显著掉档，就是模板扩充的信号——由数据驱动，不由直觉驱动。

---

## 选型 9：部署平台默认 Cloudflare Pages，Vercel 一等公民

**问题**（最新鲜的一个）：三选一等价，排序谁第一？

**决策**：Cloudflare Pages 默认。理由按权重：

1. **成本确定性**。目标用户是被 token 账单教育过的人。Vercel Hobby 档 100GB/月带宽，产品被分享一波就可能收到三位数账单的邮件；Cloudflare Pages 免费档带宽不限。"上线零成本，火了也零成本"对这个人群是杀器。
2. **架构协同**。未来 `d1://`/`r2://` adapter 让前后端同生态闭环。
3. **大陆可达性**。`pages.dev` 默认域名在大陆通常可达（慢但通），`vercel.app` 长期被污染——目标用户含中文开发者时这是现实差异。

代价诚实列出：AI 开发世界的肌肉记忆是 "deploy to Vercel"，Supabase 官方模板也默认 Vercel，熟悉度上我们逆风。对冲方式是**命令对称**（`npx wrangler pages deploy dist` vs `npx vercel --prod`，同一份产物）+ 验收线双平台各跑一次"10 分钟三条命令"。

**证伪条件**：若遥测显示 Vercel 命令的使用率碾压 wrangler（比如 10:1），说明熟悉度权重高于成本权重，默认换回来——一天的事。

---

## 选型 10：验收标准是"10 分钟三条命令"，不是功能清单

**问题**：怎么定义"做完了"？

**决策**：M3 里程碑的验收线是——**新人从 `npm create aiflow-app` 到部署 URL 可访问，≤ 10 分钟，Vercel 与 Cloudflare Pages 各跑一次。**

"落地"这个词太软，软标准必然在开发过程中被稀释成功能清单。把落地定义成可测量的操作序列（三条命令、十分钟、真实 URL），项目就有了自我证伪的能力：跑不通就是没做完，没有辩论空间。

这也是整个项目唯一的元原则：**每个承诺都要能被一个数字证伪。** 首过率证伪"AI 一次写对"，修复 token 压缩比证伪"落地成本下降"，10 分钟证伪"三条命令"。

---

## 结语：选型的元原则

回头看这十个决策，它们共享同一个底色：**在 AI 时代做基础设施，你的对手不是别的库，是"AI 现场手搓一切"的默认路径。**

所以每个选型问的都是同一个问题的变体：这件事，是让 AI 少写一段会出错的代码，还是多给 AI 一段会出错的代码？契约收敛（选型 2）、adapter 隔离（选型 3/4）、模板即 few-shot（选型 8）、可证伪验收（选型 10）——全部是前者的变体；任何形式的"全都要"（选型 1/6 的备选案）都是后者的入口。

AI 越强，执法类约束越该退役，但有两样东西不贬值：**验证过的正确性**（988 个测试背书的组件），和**判断力**（该长什么样的设计 token、该指向哪条落地路径）。Starter 是把这两样打包成三条命令的尝试。

它撑不撑得住，下个季度的首过率数据会告诉我们——这正是我们想要的那种答案。
